# テスト計画

「何をどこまで、どの環境・基準で検証するか」を定める文書。開発者と AI エージェントが**常時読む**。

受け入れ基準と非機能目標は [requirements.md](requirements.md)、業務ルールと期待動作は [specification.md](specification.md)、構造上の制約と設計理由は [architecture.md](architecture.md) に書く。**テストケースそのものは文書化しない。** 個別のケースと手順はテストコードを正とする。実行コマンドは [AGENTS.md](../AGENTS.md#commands)、実装後の品質ゲートの実行手順は `test-code` スキルに従う。

## テストスコープ

| 対象 | 自動検証の範囲 | 主な検証レベル |
| :--- | :--- | :--- |
| 難易度・FP の算出と集計（`shared/fp.ts`） | 対象 | 単体・プロパティベース・変異 |
| チャネル名と API 型（`shared/ipc.ts`） | 対象 | 単体・変異 |
| 入力検証・業務ルール・組み立て（`main/services/`） | 対象（リポジトリを差し替える） | 単体・変異 |
| IPC の窓口と登録（`main/ipc/`） | 対象 | 単体・変異 |
| 設定値の解析（`main/repositories/settings-parsing.ts`） | 対象 | 単体・変異 |
| データ格納先の解決（`main/app-paths.ts`） | 対象 | 単体・変異 |
| Excel ブックの生成（`main/export/`） | 対象 | 単体（数式の完全一致） |
| フォームのフックとエラー境界（Renderer） | 対象 | 単体・変異 |
| 表示分岐と操作可否を持つコンポーネント（Renderer） | 対象 | コンポーネント |
| DB クエリ層（`main/repositories/` のうち SQLite に触れる部分）、スキーマ移行 | 単体の対象外。E2E のシナリオが通る範囲でのみ検証する | E2E |
| アプリ全体の結線（Main・Preload・Renderer・実 SQLite） | 対象 | E2E |
| 自動更新の実配信、配布パッケージのインストール | 自動検証の対象外 | リリース時の人手確認 |

- **DB クエリ層は単体テストしない。** `better-sqlite3` が Electron 用にビルドされており、Vitest を動かす Node と ABI が合わないため（[ADR-003](architecture.md#adr-003-永続化は-sqlitebetter-sqlite3--drizzle-orm)）。純粋な設定パース処理だけは `repositories/settings-parsing.ts` へ切り出し、ネイティブバインディング無しで単体・変異テストできるようにしてある
- カバレッジと変異テストの対象ファイルは設定ファイル（`vitest.config.ts` の `coverage.include`、`stryker.config.json` の `mutate`）を正とする。新しいモジュールを足したら、対象に含めるかを同じ PR で判断する

## テストレベルと使用ツール

### 設計文書と検証の対応

| 設計文書 | 検証手段 | 担保範囲 |
| :--- | :--- | :--- |
| [requirements.md](requirements.md) の業務要件 | シナリオテスト（Playwright E2E）＋受け入れテスト（人手確認） | 起動→プロジェクト作成→機能登録→集計→再起動後の永続化、複製・デフォルト生産性変更などを通しで確認。業務全体の最終判断は人が行う |
| [requirements.md](requirements.md) の非機能要件 | 要件目標を合否条件とする検証（[非機能要件の検証](#非機能要件の検証)） | オフライン動作・永続化・標準精度・可搬性を確認。操作性「10秒以内」は人手確認 |
| [specification.md](specification.md) | インテグレーションテスト（Vitest）＋計算規則の単体・PBT | `services/` の検証・更新規則、`ipc/` の窓口、Excel 出力、UI コンポーネントの表示分岐と操作可否、FP 算出の境界・全組み合わせ |
| [architecture.md](architecture.md) | 構造による強制＋PR レビュー | TypeScript 型検査・プロセス分離・数式完全一致アサーション、および層依存・意図的不在のレビュー（[制約の強制手段](architecture.md#制約の強制手段)） |
| 詳細設計（文書にしない） | ユニットテスト（Vitest）＋変異テスト（Stryker） | 純粋ロジック・フック・エラー境界の内部仕様とテスト強度 |

### レベルとツール

| レベル | 対象 | ツール |
| :--- | :--- | :--- |
| 単体 | `shared/` の算出ロジック、`services/` の検証と組み立て、`ipc/` の窓口、Renderer の hooks、`repositories/settings-parsing.ts` | Vitest |
| プロパティベース | `analyzeFunctionPoint` の広い入力域にわたる性質 | Vitest + fast-check |
| コンポーネント | Fluent UI コンポーネントの表示分岐と操作可否 | Vitest + Testing Library（jsdom） |
| 変異 | 純粋ロジックのテスト強度 | Stryker（Vitest ランナー） |
| E2E（シナリオ） | Electron を実際に起動した通し動作（実 SQLite を含む） | Playwright（Electron） |
| 静的検査 | 書式・静的解析・型 | Prettier、ESLint、TypeScript |

- テスト名は `describe` / `it` をすべて日本語の自然文で書き、入れ子の `describe` で機能・操作ごとに束ねる（[共通実装規約](architecture.md#共通実装規約)）。テストスイートが仕様書として読めることを狙っている
- 業務ルールの表（[specification.md](specification.md#業務ルール)）はテストケースではない。テストはその行を写して書く

### 非機能要件の検証

目標の定義は [requirements.md](requirements.md#非機能要件) を正とする。

| 区分 | 検証手段 | 確かめられない範囲 |
| :--- | :--- | :--- |
| 操作性 | 受け入れテストで人が操作して確かめる | 自動計測は無い |
| オフライン動作・機密性 | 業務データを送る経路が無いことを PR レビューで照合する。E2E はネットワークに依存せず通る | 通信が発生しないことを自動で監視する仕組みは無い |
| 可搬性 | 単体テストを Windows / macOS / Linux、E2E を Windows / macOS の CI で実行する。配布物はリリースワークフローで OS ごとに作る | 配布パッケージのインストールと初回起動は人手確認 |
| データ保存 | E2E で再起動後もデータが残ることを確かめる | スキーマ移行（版数の変更）を通す自動テストは無い |
| 見積り精度 | 算出ロジックの単体・PBT と、Excel 数式の完全一致アサーション | Excel 上で再計算した結果との突き合わせは自動化していない |

## テスト環境と外部境界

| 環境 | 役割 |
| :--- | :--- |
| ローカル | 実装中の検証。`src/` で各コマンドを実行する。E2E はフルビルドしてから実行する |
| CI（[Tests ワークフロー](../.github/workflows/test.yml)） | PR・`main` への push・手動実行（`workflow_dispatch`）・Release ワークフローからの呼び出し（`workflow_call`）で、品質ゲートのすべてを実行する（[CI での実行](#ci-での実行)） |
| リリース（[Release ワークフロー](../.github/workflows/release.yml)） | Tests ワークフロー全体を通したうえで、OS ごとにパッケージングして draft に上げる。公開前の確認は人が行う（[AGENTS.md](../AGENTS.md#releasing)） |

- **単体・コンポーネントテストは jsdom 上で動かす。** 実際の Electron ウィンドウは使わない
- **E2E は実際の Electron と実 SQLite を使う。** 環境変数 `FP_STUDIO_APP_DATA_PATH` でデータ格納先をテスト専用のディレクトリへ差し替え、利用者のデータに触れない。Playwright は1ワーカーで直列に実行する
- **ネイティブ依存は Electron 向けに再構築してから E2E を実行する。** Vitest を動かす Node と ABI が合わないため、単体テストと E2E で `node_modules` を共有しない
- **テストダブルで代替する境界**:

| 境界 | 代替方法 | 理由と限界 |
| :--- | :--- | :--- |
| SQLite（`services/` から見たリポジトリ） | リポジトリを差し替えた単体テスト | ABI の制約による。実 SQLite への書き込み・取り消し・連鎖削除は E2E のシナリオが通る範囲でのみ確かめる |
| Electron API（IPC・保存ダイアログ） | 差し替えた単体テスト | 実際のダイアログ操作は自動化していない |
| `window.fpStudio`（Renderer から見た Main） | フック・コンポーネント単体では差し替える | アプリ全体のフック（`useFpStudioApp`）との結線は E2E の範囲 |
| 更新フィード（GitHub Releases） | 接続するテストを持たない | 実際の確認・ダウンロード・再起動適用はリリース時の人手確認に委ねる。テストに資格情報は不要 |

## 品質ゲートと基準

次のすべてを必須とし、1つでも失敗したら不合格とする。閾値と対象ファイルは設定ファイルを正とし、この文書には転記しない。

| ゲート | 基準 | 正本 |
| :--- | :--- | :--- |
| 書式 | Prettier の検査で差分が無い。アプリと `.github/` を対象にする | Prettier 設定、Tests ワークフロー |
| 静的解析 | ESLint のエラーが無い | ESLint 設定 |
| 型 | Node 側・Web 側の両方で型検査が通る | `tsconfig.node.json` / `tsconfig.web.json` |
| 単体・コンポーネント・PBT | すべて成功する。Windows / macOS / Linux のいずれでも成功する | Vitest 設定 |
| カバレッジ | 対象ファイルの**分岐カバレッジ**が閾値以上。E2E はカバレッジに含めない | `vitest.config.ts` の `coverage.thresholds` |
| 変異 | **変異スコア**が `break` 閾値以上 | `stryker.config.json` の `thresholds` |
| E2E | Windows / macOS の両方で全シナリオが成功する | Playwright 設定、Tests ワークフロー |

- **変異テストの対象は純粋ロジックに絞る。** Fluent UI コンポーネントと Excel ブック組み立ては、カバレッジ計測の対象には含めるが変異対象からは外す。レイアウトや書式を変異させても意味のある生存変異体にならないため。同期が要る Excel 数式は完全一致アサーションで別途守る
- **Excel 数式の完全一致アサーションは削らない。** 算出規則を変えるときは `shared/fp.ts`・Excel 数式・`project-excel.test.ts` を同じ PR で直す（[ADR-005](architecture.md#adr-005-excel-出力は値ではなく数式で書き出す)）
- **セキュリティ検証**（コード静的解析・依存関係の脆弱性監査）は現在の品質ゲートに含めない。外部 Actions はコミット SHA に固定し、CI の権限は `contents: read` に限定する

### CI での実行

[Tests ワークフロー](../.github/workflows/test.yml) はローカルの検証と同じスクリプトを使い、独立した検証にはジョブ間の依存を設けず、以下の10ジョブを並列に実行する。

| ジョブ | 環境 | 検証内容 |
| :--- | :--- | :--- |
| format / lint / typecheck / pbt（4ジョブ） | Ubuntu 24.04 | 書式、静的解析、型、PBT |
| unit（3ジョブ） | Ubuntu 24.04 / Windows 2025 / macOS 15 | 全単体テストとカバレッジ（PBT を含む） |
| mutation（1ジョブ） | Ubuntu 24.04 | 純粋ロジックの変異テスト。ジョブ内は 2 ワーカー |
| e2e（2ジョブ） | Windows 2025 / macOS 15 | フルビルドと Electron の通し動作（実 SQLite を含む） |

- **失敗しても他の検証結果を収集する。** matrix の `fail-fast` は無効。同じブランチの新しい実行が始まった場合は古い実行をキャンセルし、更新前の検証にランナーを使い続けない
- **環境を揃え、ネイティブ依存を混在させない。** 共通の [セットアップ Action](../.github/actions/setup/action.yml) で Node.js を固定し、`package.json` の `packageManager` に指定した pnpm とロックファイルで復元する。キャッシュは pnpm ストアに限定し、OS と Electron ABI に依存する `node_modules` はジョブ間で共有しない
- **取得時間を E2E のテスト時間に含めない。** Electron バイナリは最初のテストより前に取得し、ネイティブ依存を Electron 向けに再構築してからビルド・テストする
- **書式検査はファイルを書き換えない。** アプリと `.github/` を検査し、カバレッジ・変異レポート・E2E 結果・Stryker の一時ファイルは除外する
- **合否の基準はローカルと共通。** カバレッジと変異スコアは既存の設定ファイルに従う。全単体テストはカバレッジ計測時に実行し、同じジョブで重複実行しない
- **失敗を調査できる成果物を残す。** カバレッジ、変異レポート、E2E 結果（失敗時の trace を含む）は失敗時もアップロードを試み、7日間保存する
- **実行権限を限定する。** 標準の GitHub ホストランナーを使用し、権限は `contents: read`、外部 Actions はコミット SHA に固定する

実行コマンドと結果の確認方法は [AGENTS.md](../AGENTS.md#commands) を参照する。ジョブ構成、ランナー、バージョン、タイムアウト、保存期間の正はワークフローと共通セットアップ Action とする。

## 終了条件

**実装 PR を Ready for review にする条件**

- ローカルで `test-code` スキルの品質ゲートを通し、CI の Tests ワークフローの全ジョブが成功している
- 振る舞いを変えた場合、対応する設計文書（[specification.md](specification.md)・[architecture.md](architecture.md)・この文書）が同じ変更に揃っている
- 自動で確かめられなかった観点（[重点リスクと検証限界](#重点リスクと検証限界) の「限界」に当たるもの、人手確認が必要な非機能目標）を、確認済みか未確認かを区別して PR 本文に記録している

**人の受け入れテストへ渡す条件**

- `main` で Tests ワークフローが成功している
- リリースの場合は、draft リリースに更新情報（`latest*.yml`）と差分ファイル（`.blockmap`）がそろい、各 `url` がアップロード済みの成果物名と一致している（[AGENTS.md](../AGENTS.md#releasing)）
- draft の公開は利用者に更新が配信される操作のため、人が受け入れテストの結果をもとに判断する

## 重点リスクと検証限界

何が壊れやすく、どのレベルで確かめるか。個別のケースと手順はテストコードを正とする。ここに挙げた観点がすべてテストへ反映済みであることを、この文書は保証しない。

| 対象 | 重点リスクと確かめ方 | 限界 |
| :--- | :--- | :--- |
| 難易度・FP の算出 | **境界値が最大の急所。** DET は `<`、参照数は `<=` で判定が変わるため、各 Function Type の閾値ちょうどの値を両側から確かめる。全 Function Type × 全バケットの組み合わせを網羅する。設定由来の規則・重みを渡したときに既定値ではなくそちらが使われること、欠けた項目だけ既定値へフォールバックすることを確かめる。単体テストとプロパティベーステストの両方をかける | — |
| 集計 | 機能 0 件の合計と、概算工数の丸めの桁 | — |
| Excel 出力 | **生成される数式文字列の完全一致を確かめる。** TypeScript 実装との同期を守る唯一の仕掛けで、数式を変えるときは `project-excel.test.ts` の完全一致アサーションを必ず一緒に直す。シート名・参照範囲・`Summary` の生産性セル参照が崩れていないこと、ファイル名の整形も確かめる。同梱する表に設定の値が使われ、欠けた項目が標準値で補われて空のセルができないこと、備考の列を足しても既存の列が動かないことを確かめる | 文字列の一致は、数式と TypeScript 実装の計算結果が全入力域で一致することの証明ではない。Excel 上で実際に再計算した結果との突き合わせは自動検証の範囲外 |
| `services/` の検証 | 不正入力がそれぞれ固有のメッセージで弾かれること、対象が存在しないときのメッセージ、プロジェクトの更新日時が更新されること | リポジトリを差し替えた単体テストであり、実 SQLite への書き込みは確かめない |
| 生産性のフォールバック | プロジェクト個別値が未設定・非数のときだけ既定値が使われること、丸めが保存値に効くこと、丸めると 0 になる値が丸めた後の検証で弾かれること（プロジェクトの生産性とデフォルト生産性の両方） | 同上 |
| 複製 | 名前・説明・生産性・全機能の引き継ぎと、ID が新しくなること | 同上 |
| トランザクション | 複数の書き込みを伴う操作（複製、機能の追加・編集・削除）が、1つのトランザクションの中で書き込みを行うこと。リポジトリを差し替えたサービス層の単体テストで確かめる | 張り忘れは検出できるが、取り消しそのもの（途中で失敗したら何も残らないこと）は SQLite の保証に委ねており、自動検証していない |
| フォームのフック | プレビューが出る条件と出ない条件、送信可否の判定、編集モードの開始・キャンセル・リセットで状態が戻ること、現在値と同じ生産性を保存できないこと | フック単体の検証であり、画面との結線は保証しない |
| 機能入力フォーム（コンポーネント） | モードによる見出しの切り替え、プレビューの有無による表示、処理中と送信可否によるボタンの無効化、編集モード中は折りたたまれないこと | jsdom 上の検証であり、実際の Electron ウィンドウでの表示は E2E の範囲 |
| 設定ビュー・アップデート通知カード（コンポーネント） | デフォルト生産性の入力と保存の可否、処理中の無効化、難易度ルールと重みを編集する入力欄が無いこと。アップデート状態ごとの「更新を確認」「今すぐインストール」の可否 | jsdom 上の検証であり、実際の Electron ウィンドウでの表示は E2E の範囲。アプリ全体のフック（`useFpStudioApp`）との結線は単体では確かめておらず、E2E の範囲 |
| IPC 登録 | 業務用の全チャネルが登録され、登録の前に解除されていること（多重登録の防止） | アップデート用のチャネルは対象外 |
| 設定の解析 | 壊れた JSON・欠損キー・型違いのときに既定値へフォールバックし、例外を投げないこと | ネイティブ依存なしで確かめられるのは解析だけ。設定の読み書きのクエリは E2E の範囲 |
| パス解決 | 期待値を `join()` で組み立てて比較する。区切り文字を直書きすると Windows で落ちる | — |
| E2E | 起動 → プロジェクト作成 → 機能登録 → 集計表示 → 再起動後もデータが残っていること。デフォルト生産性の変更が以後に新規作成するプロジェクトにだけ効き、再起動後も残ること。複製で全機能が引き継がれること | **実 SQLite を通る唯一の検証。** DB クエリ・トランザクションによる取り消し・外部キーによる連鎖削除・スキーマ移行は、E2E のシナリオが通る範囲でしか確かめられない。CI の E2E は Windows / macOS のみで、Linux での通し動作は自動検証していない |
| 自動更新の実配信 | リリース時の draft 検証と実機確認 | GitHub Releases を介した実際のダウンロード〜再起動適用は自動テストの範囲外。macOS は未署名のため自動更新が動かない（[ADR-009](architecture.md#adr-009-リリースを-github-actions-で行い当面はコード署名しない)） |
